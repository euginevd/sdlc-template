What you want built and why, in your own words, written at the start and updated when it changes. The `new-project` interview asks its questions and the agent writes your answers in for you to check. The agent drafts [spec.md](spec.md) from it but never changes your words unasked; where the two differ, the spec is what gets built. Each later change has its own intent: a GitHub issue with the same headings. The repo may be public, so no real balances, keys or personal details: those stay in `local/`, which git ignores.

## Intent

1. Problem: *(to fill in)* what's wrong today, and for whom.
2. Proposed outcome: *(to fill in)* what you want built, and the few things the first version must do, by screen or tab, with what goes in and comes out.
3. Affected users and systems: *(to fill in)* who uses it first and who after (just you, then friends, then customers or open source), and the systems it touches.
4. Constraints: *(to fill in)* where it runs first, such as local Docker or AWS `dev`, and the lines it never crosses: keys, money, data, accounts and what's exposed publicly.
5. Success criteria: *(to fill in)* how you'll know the first version works: checks a person can run, such as "a new user signs up and sees their dashboard".
6. Open questions: *(to fill in)* what's still undecided, and ideas for later, or none. One becomes a GitHub issue when you say.
