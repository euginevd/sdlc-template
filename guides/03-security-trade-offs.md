# Security trade-offs

The risks the template accepts for speed, each with why it's a risk and the fix for production. Numbered so reviews can cite them (trade-offs 1). An accepted risk is a decision: change it here, never by weakening a check.

A project's profile decides what happens to them ([AGENTS.md](../AGENTS.md) rules 15 and 24). A `prototype` accepts them all. A `production` project applies each production fix, or records in `decisions.md` who accepts the risk; 12 and 13 are the prototype's own and never apply to it.

| # | Risk | Why it's a risk | Production fix |
|:-:|------|-----------------|----------------|
| 1 | The agent shares the developer's GitHub identity | It runs `gh` with the developer's token, so it could merge its own PR, leave review threads open, approve its own deploy, edit the apply environments or delete the ruleset; only `AGENTS.md` rules 13, 20 and 21 ask it not to | A second reviewer: `bash scripts/protect-main.sh production` makes the `main` ruleset require their approval after the last push, with every thread resolved, and the apply environments name them with *Prevent self-review* on |
| 2 | Nothing enforces the agent's rules on the machine | It runs with the developer's files and credentials, so only `AGENTS.md` rules 20 and 21 stop it reading `.env` files and secrets, skipping a hook or changing cloud resources | Deny rules in the agent's own settings (Claude Code: `.claude/settings.json`) or a sandbox, covering `.env*` (except `.env.example`), `*.tfvars`, `git push --no-verify`, `terraform apply` and `aws`; secrets in a vault, not in local files |
| 3 | Pinned tools go stale | Dependabot doesn't update the scanner, Terraform, Python and Node images pinned by digest in the workflows, `TF_VERSION`, or the tools on a developer's machine, so they age and miss newer checks. `setup.sh --check` shows where a machine differs from the pipeline | Renovate, which opens update PRs for those pins with the same 7-day wait; until then, update them by hand when changing a workflow |
| 4 | The deploy role is broad in two places | `apigateway:*` covers every API in the region, because API Gateway ARNs use generated IDs, and the log delivery actions need `*`. In a shared account, the pipeline could change another workload's API or log policies | A dedicated AWS account per project and environment, so there's nothing else in reach |
| 5 | Plans run unreviewed code and are kept as files | The `plan` job runs a PR's Terraform with the read-only role before anyone reviews it, so a PR can read the state; and the saved plan holds state values in plain text, downloadable for a day by anyone who can read the repo, which on a public repo is anyone signed in to GitHub | A private repo, a required reviewer on the plan environments, and plans encrypted before upload |
| 6 | A failing Terraform plan can merge | The `aws` workflow runs only when infrastructure, apps or packages change, so `plan` can't be a required check. The required `terraform` check validates every unit, so only an error that needs AWS to find gets through, and a unit whose plan failed is never applied | A small job that always runs, fails only when a plan failed, and is a required check |
| 7 | A PR's checks cover only what it changes | To keep PRs fast, Gitleaks scans only the PR's commits, Semgrep reports only findings it adds, the app jobs run only for the apps it changes, and CodeQL skips docs-only PRs. A new scanner rule that matches older code fails only the runs on `main` and the weekly run, which block nothing; and a file the `changes` job files under the wrong app skips that app's checks | Alerts for failed runs on `main` and the weekly scans, fixed like a failed PR; the `changes` job's paths reviewed when the repo's layout changes |
| 8 | Some checks are missing | The workflows aren't linted, though agents edit them (`AGENTS.md` rule 10); the two report scripts that write the PR summaries have no tests or type checks; Terraform is validated but not linted; and `code-standards.md` 20 asks for model evals in CI, with no job for them | actionlint or zizmor, and tflint, from pinned images as required checks; tests for the scripts, with pyright and coverage including `scripts/`; an evals job once an app calls a model |
| 9 | CodeQL needs a paid plan on private repos | Code scanning with CodeQL is free on public repos only; on a private repo without GitHub Code Security the `codeql` workflow skips itself, so Semgrep is the only static analysis | Buy GitHub Code Security, or accept Semgrep alone and record it in `decisions.md` at kickoff |
| 10 | Cost is a warning, not a gate | The cost comment flags a plan above `MONTHLY_COST_LIMIT` but doesn't block the merge, and it prices only what Terraform creates, not usage such as model tokens and data transfer. The budget emails on actual spend, up to a day late and for the whole account, and stops nothing | A required check that fails above the limit, plus Cost Anomaly Detection and a budget per project through cost allocation tags |
| 11 | Nothing checks kickoff was finished | A line still marked *(to fill in)* in `docs/` is a decision nobody made, and a threat model or costs doc left as the starter's describes the sample, not the project; only the kickoff gate (`AGENTS.md` rule 15) catches it | A CI check that fails while *(to fill in)* is still in `docs/` once `PROJECT_NAME` is set |
| 12 | A prototype runs without human gates | Nobody approves its plan, its merges or its `dev` deploys, and the agent settles unclear points itself (`AGENTS.md` rule 24), so a wrong design or a bad change is live in `dev` before anyone looks; the scans and required checks are the only gate | The `production` profile, with the second reviewer in 1 |
| 13 | A prototype is lightly tested | Its tests cover main paths and sensitive code only, with one review per branch and no threat model unless asked (`AGENTS.md` rule 24), so edge cases and regressions surface late | Before it becomes `production`: a threat model, its abuse-case tests, coverage back to 80% and a review in every phase |
