# Security trade-offs

The risks the template accepts for speed, each with why it's a risk and the fix for production. Numbered so reviews can cite them (trade-offs 1). An accepted risk is a decision: change it here, never by weakening a check.

A project's profile decides what happens to them ([AGENTS.md](../AGENTS.md) rules 15 and 24). A `prototype` accepts them all, 14 and 15 included. A `production` project applies each production fix, or records in `decisions.md` who accepts the risk; 14 and 15 never apply to it.

| # | Risk | Why it's a risk | Production fix |
|:-:|------|-----------------|----------------|
| 1 | The agent shares the developer's GitHub identity | It runs `gh` with the developer's token, so it could merge its own PR, approve its own deploy, edit the apply environments or delete the ruleset; only `AGENTS.md` rules 20 and 21 ask it not to. A prototype accepts this: nothing real is at stake | A second reviewer, required for `production`: `bash scripts/protect-main.sh production` makes the `main` ruleset demand one approval from someone other than the author, after the last push, and the apply environments name that reviewer with *Prevent self-review* on, so the agent can't merge or deploy alone |
| 2 | Pinned scanner and CI images go stale | The gitleaks, Trivy, Checkov, Semgrep, Infracost, Terraform, Python and Node images are pinned by digest in `docker run` and `container:` lines, which Dependabot doesn't update, so the scanners age and miss newer checks. The same goes for `TF_VERSION` in the `aws` workflow and the tools `setup.sh` installs on a developer's machine | Renovate, which opens update PRs for those digests with the same 7-day wait; until then, update the pins by hand when changing a workflow |
| 3 | The deploy role is broad in two places | `apigateway:*` covers every API in the region, because API Gateway ARNs use generated IDs, not names; the log delivery actions, such as `logs:PutResourcePolicy`, need `*`. In a shared account, the pipeline could change another workload's API or log policies | A dedicated AWS account per project and environment, so there's nothing else in reach |
| 4 | A failing Terraform plan can merge | The `aws` workflow runs only when `infra/aws/`, `apps/`, the Python packages or the workflow changes, so `plan` can't be a required check. The required `terraform` check formats and validates every unit, so only an error that needs AWS to find gets through; nothing broken reaches AWS, because a unit whose plan failed has no saved plan and is never applied | A small job that always runs, fails only when a plan failed, and is a required check |
| 5 | A PR's checks cover only what it changes | To keep PRs fast, Gitleaks scans only the PR's commits, Semgrep reports only findings it adds, the app jobs run only for the apps it changes, and CodeQL skips docs-only PRs. A new scanner rule that matches older code fails only the run on `main` or the weekly run, which block nothing; and a file the `changes` job files under the wrong app skips that app's checks. Unknown paths, and a failed `changes` job, run everything | Get alerts for failed runs on `main` and the weekly scans, and fix them like a failed PR; review the `changes` job's paths when the repo's layout changes |
| 6 | Cost is a warning, not a gate | The cost comment flags a plan above `MONTHLY_COST_LIMIT` but doesn't block the merge, and it prices only what Terraform creates, so usage such as model tokens and data transfer shows as nothing. The bootstrap stack's budget emails on actual spend, up to a day late and for the whole account, and stops nothing | A required check that fails above the limit, plus Cost Anomaly Detection and a budget per project through cost allocation tags |
| 7 | CodeQL needs a paid plan on private repos | GitHub's code scanning with CodeQL is free on public repos only; on a private repo without GitHub Code Security, the `codeql` workflow can't upload results, so Semgrep is the only static analysis that runs | Buy GitHub Code Security for the organisation, or accept Semgrep alone and record it in `decisions.md` at kickoff |
| 8 | Nothing enforces the agent's rules | `AGENTS.md` rules 20 and 21 ask the agent not to read `.env` files and secrets, skip a hook or change cloud resources, but it runs with the developer's files and credentials, so only the rules stop it | Deny rules in the agent's own settings (Claude Code: `.claude/settings.json`) or a sandbox, covering `.env*` (except `.env.example`) and `*.tfvars`, `git push --no-verify`, `terraform apply` and `aws`; secrets in a vault such as Secrets Manager, not in local files |
| 9 | Plans run unreviewed code and are kept as files | The `plan` job runs a PR's Terraform with the read-only role before anyone reviews it, so a PR can read the state; and the saved plan holds state values in plain text, which anyone who can read the repo can download for a day: on a public repo, anyone signed in to GitHub | A private repo, a required reviewer on the plan environments, so a plan runs only once someone has seen the code, and plans encrypted before upload |
| 10 | Workflows and report scripts aren't linted or tested | Agents edit the workflows (`AGENTS.md` rule 10), and CodeQL's scan of them runs on public repos only; `security-report.py` and `cost-report.py`, which write the summaries a merge relies on, have no tests or type checks | actionlint or zizmor from a pinned image as a required check; tests for both scripts, with pyright and coverage including `scripts/` |
| 11 | A PR can merge with open review threads | A prototype's ruleset doesn't require threads to be resolved, so only `AGENTS.md` rule 13 makes the agent answer each finding | `bash scripts/protect-main.sh production`, which requires it along with the second reviewer in 1 |
| 12 | Nothing checks the worked example was replaced | A doc left over from `travel-claims` reads as the project's own settled decision, which the agent won't reopen; only the kickoff gate (`AGENTS.md` rule 15) catches it | A CI check that fails while `travel-claims` or `Wattle` is still in `docs/` once `PROJECT_NAME` is set |
| 13 | Terraform isn't linted and model evals have no job | `terraform validate` catches syntax and type errors, not what tflint knows about each provider, such as an invalid instance type; `code-standards.md` 20 asks for evals in CI, and the template has no job for them | tflint in the `terraform` check; an evals job as a required check once an app calls a model |
| 14 | A prototype runs without human gates | Nobody approves its plan, its merges or its `dev` deploys, and the agent settles unclear points itself (`AGENTS.md` rule 24), so a wrong design or a bad change is live in `dev` before anyone looks; the scans and required checks are the only gate | The `production` profile, with a required reviewer on the apply environments |
| 15 | A prototype is lightly tested | Its tests cover main paths and sensitive code only, with one review per branch and no threat model unless asked (`AGENTS.md` rule 24), so edge cases and regressions surface late | Before it becomes `production`: a threat model, its abuse-case tests, coverage back to 80% and a review in every phase |
